TL;DR

  1. Production config for Qwen3.5-9B (updated 2026-05-24): beellama + Q8_0 weights + turbo4 KV at 64K context, no spec. Validated 10/10 NIAH retrievals, median TTFT 7.58s, sustained 71 tok/s at 60K input, peak VRAM 9.7 GB. (Previously turbo3_tcq at 39 tok/s — swap is a free 82% speedup.)
  2. DFlash adds VRAM and rarely helps for 9B. Draft model + spec workspace costs ~1.5 GB; only pays off in tok/s above ~500 output tokens at long context.
  3. vLLM cannot do TQ + speculative decoding combo today. All 3 forks investigated either gate it off or don't have spec at all. beellama is the only OpenAI-compatible HTTP server with TQ + DFlash working.
  4. F16 KV at 128K does NOT OOM on 9B (~13 GB peak) — llama.cpp -fa on stores KV ~3.6× more compactly than textbook math predicts.
  5. Lucebox full stack (PFlash + TQ + DFlash + DDTree) on 27B at 128K peaks at ~19-20 GB — the only path to run 27B at 128K on a 24GB card.

Running Qwen3.5-9B alongside SoulX video gen, Whisper STT, Kokoro TTS, VAD on a single 24GB 4090:

Cross-stack reference: Lucebox PFlash 27B @ 128K

The full PFlash + DFlash + TQ + DDTree stack on Qwen3.6-27B Q4_K_M, the only viable path for 27B + 128K on a 24GB card.

SetupPeak VRAMFits on 24 GB?
27B + F16 KV naive (no compression)~36 GB✗ OOM by 12 GB
27B + TQ3 KV only~22 GBvery tight
27B + PFlash + TQ3 + DFlash + DDTree (Lucebox)~19-20 GB✓ comfortable

PFlash's 20× input compression (131K → 6.5K tokens via drafter scoring) is the dominant VRAM lever — shrinks the KV cache before TQ even gets to work on it.

Lucebox claims 24.8s TTFT at 128K on RTX 3090 native Linux. Our RTX 4090 WSL2 measured ~157s (6.5× slower). Root cause not isolated; sm_86 kernel fallback, JIT warmup, and BSA disabling all ruled out. See docs/findings/2026-05-24-pflash-128k-direct-vs-http.md.

Memory math: Qwen3.5 is a HYBRID architecture (only 8 of 32 layers cache KV)

Initially I predicted F16 KV at 131K ≈ 16 GB but measured was 4.4 GB. I attributed this to llama.cpp's flash-attention layout. That was wrong. The real cause is in the server log:

llama_kv_cache: size = 4224.00 MiB (135168 cells, 8 layers, 4/1 seqs),
                K (f16): 2112.00 MiB, V (f16): 2112.00 MiB
llama_memory_recurrent: size = 201.00 MiB (4 cells, 32 layers, 4 seqs),
                R (f32): 9.00 MiB, S (f32): 192.00 MiB

Only 8 of 32 layers store an attention KV cache. The other 24 layers are recurrent/SSM-style with constant ~200 MB total regardless of context length.

Independently confirmed in vLLM v0.21.0 startup log: TQ hybrid: full-attention layers [3, 7, 11, 15, 19, 23, 27, 31] — exactly 8, every 4th of 32. Qwen3.5 is in the Jamba / Falcon-H1 family of hybrid attention+SSM models.

Corrected per-token KV math

8 full-attn layers × (K + V) × n_embd_k_gqa × 2 bytes
= 8 × 2 × 1024 × 2 bytes = 32 KiB/token

131,082 tokens × 32 KiB = ~4.1 GB ✓ (matches measured 4,425 MiB)

Per-method savings — corrected

MethodPer-token (attn only)131K totalvs F16
F16 (8 attention layers)32 KiB4.2 GB1.0× (baseline)
TQ3_tcq (8 attention layers)~8 KiB~1.0 GB~4× compression ✓
Recurrent state (24 layers)n/a (fixed state)constant ~0.2 GBdoesn't compress
Implication: TQ KV compression is less impactful on Qwen3.5 than on pure-attention models because only 25% of layers contribute to the cache that scales with context.
  • Pure-attention 32-layer Llama-3-9B-ish at 128K: F16 KV ≈ 16 GB → TQ3 saves ~12 GB
  • Qwen3.5-9B hybrid at 128K: F16 KV ≈ 4 GB → TQ3 saves ~3 GB
This explains why the headline VRAM win on 9B was modest — the architecture is already KV-frugal by design. TQ's value will be larger on traditional attention models, especially at longer contexts.

How to detect a hybrid GGUF

Check the startup log for llama_kv_cache: size = X MiB (N cells, K layers, ...). If K < n_layer, the model is hybrid.

Methodology

Test harness

Python httpx.stream(...) drives streaming chat completions over SSE. Per-chunk timestamps captured for TTFT and inter-token latency. Output collected as single string for substring-match validation.

NIAH prompt construction

Used lucebox-hub/pflash/tests/niah_gen.py:

  • Filler: "The grass is green. The sky is blue. The sun is yellow. Here we go. There and back again. " (repeated)
  • Needle: "The special magic {key} number is: {value}." at random position (25-75% through)
  • Question: "What is the special magic {key} number? Answer in one short sentence."
  • Tokenizer: Qwen/Qwen3.5-9B, binary search to land within 0.5% of target token count

VRAM measurement

Background nvidia-smi --query-gpu=timestamp,memory.used,utilization.gpu --format=csv -l 2 CSV. Peak extracted via awk.

Server readiness probe

llama.cpp /health returns 200 before model loading completes. We probe /v1/chat/completions with a 1-token request instead, treating HTTP 200 (not 503/400) as the ready signal.

Known failure modes encountered

  • Q4_K_M DFlash draft missing tokenizer merges → use Q8_0 variant only
  • /health false-positive readiness
  • Prompt 131,082 tokens vs -c 131072 → 400 reject; bump context slightly
  • Thinking mode kills speculative decoding → always disable via --reasoning-format none
  • vLLM TQ + spec silently disabled (no error)
  • WSL2 ptrace_scope=1 blocks py-spy → use cProfile via SIGTERM dump
  • pkill -f kills parent bash shell when pattern matches PATH expansion → kill by specific PID

TurboQuant variant comparison ⭐ (added 2026-05-24)

After initial Group D shipped with turbo3_tcq as default, we swept other beellama TurboQuant KV variants on the same 10 NIAH @ 60K cases through the Docker image. Result: turbo4 is 82% faster than turbo3_tcq at identical accuracy.

VariantBitsEncodingAccuracyTTFT mediantok/sPeak VRAM
turbo4 ⭐ (new default)4raw10/107.58s71.49,734 MiB
turbo33raw10/106.63s47.39,862 MiB
turbo3_tcq (old default)3TCQ-encoded10/108.96s39.29,878 MiB
  • All three variants preserve NIAH retrieval quality at 100% — TurboQuant KV doesn't degrade long-context behavior at 3 or 4 bits
  • TCQ encoding's bit savings are lost in measurement noise (~140 MiB difference) but its decode cost is real (~40% slower than raw 3-bit)
  • turbo4 wins because the simpler 4-bit kernel runs much faster, with sub-1% VRAM cost
  • Production deployment defaults swapped to turbo4 in docs/deployment/docker/ .env.example, Dockerfile, compose.yml, README, and the integration guide

Bonus run — vLLM v0.21.0 TurboQuant on Qwen3.5-9B-FP8 (failed, but informative)

Tried vllm/vllm-openai:v0.21.0 with --kv-cache-dtype turboquant_k3v4_nc on lovedheart/Qwen3.5-9B-FP8, single-slot, 64K context, to directly compare VRAM to beellama's ~10 GB.

Hit two distinct bugs.
  1. OOM at --gpu-memory-utilization 0.55 (13.5 GB cap). FP8 9B weights + vLLM compile/Triton/CUDA-graph overhead consumed ~13 GB, no room for KV pool. Even --enforce-eager + 4K context failed. Error: ValueError: No available memory for the cache blocks.
  2. TurboQuant workspace assertion at long context at 0.75 (18 GB cap): 
    AssertionError: Workspace is locked but allocation from
'turboquant_attn.py:747:_continuation_prefill' requires 8.00 MB,
current size is 0.51 MB. Workspace growth is not allowed after locking.
    Same class of bug as Issue #42808 — TQ workspace pre-sized at warmup, locked, then real long prefill needs more and asserts. Issue was filed for TQ+MTP but also fires on TQ+long-context without spec.

VRAM comparison (corrected interpretation)

vLLM at --gpu-memory-utilization 0.75 --max-model-len 65536 allocated 16,936 MiB at steady state. Estimated breakdown:

ComponentMiBbeellama equivalent
FP8 weights (vs beellama Q8 GGUF 8,045)~8,900~8,045
torch.compile/Inductor cache~500-1,0000 (no JIT)
Triton kernel scratch (TQ)~500~100
CUDA graph capture (sizes [1,2])~1,000-2,0000 (no graphs)
KV cache pool reservation~3,000-4,000~700 (actual KV)
Block table / scheduler state~300~0
Total~16,9369,878

vLLM is ~7 GB heavier than beellama at this workload. Roughly 3-4 GB is genuinely needed (compile, CUDA graphs, Triton, paged block manager); the rest is pool over-allocation that comes from --gpu-memory-utilization policy, not actual need.

Why we didn't retry: even with PR #40914's workspace fix cherry-picked, vLLM's runtime overhead structurally exceeds beellama for single-user use. beellama wins by being simpler (no JIT, no CUDA graphs, no paged manager) at the cost of no continuous batching — fine for our use case.
